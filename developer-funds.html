Ways to send and receive funds

These are the fund-movement paths the platform supports, with what each one does right now. Internal ledger operations are ready to use; anything that leaves the platform is labelled with the provider or approval it still needs.

One rule before you start: a ledger credit, an authorization, a message draft, or a successful API response is not proof that external money has settled. Treat a rail as live only after its provider credentials, account ownership, compliance approvals, webhook delivery, and reconciliation process have been tested and approved.

What you can do today

Every path below is implemented in the platform. The badge tells you the current state of each one.

Live · operator JWT

1. Transfer between wallets or merchant ledger accounts

This path posts a double-entry ledger transfer immediately. In the current API, wallet and generic transfer routes live under /admin and require an administrator/operator JWT. Never give an admin token to a customer or embed one in a browser app.

Step by step

  1. Have an authorized operator confirm both wallets/accounts are provisioned, active, and in the same currency. Confirm the sender has enough available balance, including any configured fee.
  2. Read the current balance and statement from the secured admin API; use the assigned API host and the exact /admin/wallets route family.
  3. For one wallet-to-wallet transfer, call POST /admin/wallets/:address/transfer with the destination address, amount, currency, and a useful description.
  4. For a batch, call POST /admin/transfers/bulk. The batch accepts wallet or merchant sources, up to 1,000 items, and items can complete or fail independently. Inspect every item result.
  5. Save each returned transfer reference. Verify the destination credit and source debit in the ledger statement before marking the business order paid.
{
  "destinationAddress": "WALLET_RECEIVER",
  "amount": "25.00",
  "currency": "USD",
  "description": "Order 1042"
}
GET /admin/wallets/:address/balanceGET /admin/wallets/:address/statementGET /admin/transfers/:reference
Internal only: POST /admin/wallets/:address/fund credits from a system funding ledger account. It is an accounting operation, not a customer bank deposit or proof of external funds received.
Live · merchant HMAC

2. Send between two terminals (T2T)

T2T debits the sending terminal account and credits the receiving terminal account in the same merchant ledger, atomically. It moves value inside a single merchant — it is not a bank transfer and does not move value between different merchants.

Step by step

  1. Get both terminal IDs provisioned and active under the same merchant. Confirm their ledger accounts are enabled for the requested currency.
  2. Ask an authorized operator to add the sender server's fixed public IP to the T2T allowlist. Call POST /t2t/ping from that IP and resolve any allowlist or authentication issue first.
  3. From your backend only, sign the exact JSON body with the assigned merchant HMAC key. Send the required x-primestack-key-id, timestamp, nonce, and signature headers.
  4. Call POST /t2t/transfer with a new URL-safe x-primestack-idempotency-key of at least 16 characters for each new transfer. Use the same key only when retrying that exact request.
  5. Accept the operation only when the response reports COMPLETED. Store its reference and journal entry reference; verify both terminal balances with GET /t2t/balance/:tid?currency=USD.
{
  "sourceId": "TERM_SENDER",
  "destId": "TERM_RECEIVER",
  "amount": "25.00",
  "currency": "USD",
  "description": "Order 1042"
}
POST /t2t/pingPOST /t2t/transferGET /t2t/balance/:tidPOST /t2t/whitelist (operator only)

Whitelist a sender IP

  1. The sender sends its fixed public egress IP and a public HTTPS callback URL to the platform operator.
  2. An authorized operator or merchant calls POST /t2t/whitelist with {"ip":"...","action":"add"} and the optional callbackUrl. This route uses a JWT, not the merchant HMAC signature.
  3. The platform stores the entry, probes that IP on TCP 443 then 80, and POSTs a signed {"event":"t2t.whitelist.ping",...} notice to the callback so the sender knows the entry is reachable.
  4. List the current entries with GET /t2t/whitelist, or probe them again with POST /t2t/whitelist/ping.
  5. The allowlist entry — not the ping result — is what authorizes a transfer. A non-allowlisted IP is rejected with 403 even when it can reach the API, and a reachable ping never grants access on its own. The callback notice is optional and diagnostic: with no callbackUrl, or when a delivery fails, the sender can still transfer.
  6. The allowlist compares the caller IP that reaches the API, so trust-proxy settings must be correct on the server. Behind a reverse proxy (for example Render) set TRUSTED_PROXIES to the proxy ranges so the real client IP is used; otherwise every request looks like it came from the proxy and no sender IP can ever match.

Ping the platform before you send

  1. Call POST /t2t/ping from the exact IP you sent for allowlisting. It is signed like every other T2T request.
  2. A successful response proves the platform, your credentials, clock skew, and the allowlist are all correct. Resolve any error before sending funds.
  3. Use POST /t2t/whitelist/ping to re-probe an allowlisted IP on TCP 443/80 and re-deliver the reachability notice.

Live · merchant HMAC + connection signature

3. Receive a payment from another PrimeStack deployment (S2S)

The receiving deployment validates a registered connection, enforces its currency and amount limits, credits the selected local wallet, and stores a payment and journal reference. The sending partner still confirms its own debit and any external settlement.

Step by step

  1. Agree with the peer on the HTTPS endpoint, supported currencies, limits, allowed source IPs, callback behavior, and reconciliation references.
  2. Register an S2S connection using POST /s2s/connections. Exchange the connection secret securely and store it in server-side secret managers only.
  3. Ensure the recipient wallet is active and denominated in the payment currency. Test the connection with POST /s2s/connections/:id/ping.
  4. The sending peer posts to POST /s2s/connections/:id/receive. Include normal merchant HMAC headers and the S2S timestamp, nonce, signature, and idempotency headers. Each new payment needs a fresh nonce and idempotency key.
  5. Check the response and then query GET /s2s/payments?connectionId=:id. Save the PrimeStack payment reference, sender reference, and journal entry reference; reconcile these with the peer before treating the payment as externally settled.

x-s2s-nonce: <fresh-unique-value>
x-s2s-signature: <HMAC-SHA256>
x-s2s-idempotency-key: <unique-for-this-payment>

Authorization / capture / ledger settlement

4. Card or POS transaction workflow

The API runs the full authorize → capture → reverse lifecycle and posts settlement accounting. The current /transactions/authorize implementation validates and records an authorization and selects a route, but does not itself send an authorization request to an external card network or acquirer.

Step by step for an approved test integration

  1. Obtain a registered active merchant and terminal, an approved acquirer/host setup, scheme rules, and a certified test environment. Use only provider-approved test data until the complete external connection is verified.
  2. Call POST /transactions/authorize with the terminal ID, amount, currency, and permitted non-sensitive transaction fields. Keep card data out of browser code and logs.
  3. Proceed only when the response is approved. Save the returned STAN and transaction ID. An authorization is not captured or settled money.
  4. After your approved acquirer capture step succeeds, call POST /transactions/capture with the STAN, RRN, and captured amount so PrimeStack records it for settlement.
  5. An authorized operator runs POST /settlement/batches for the merchant, date, and currency. Check the batch, fees, ledger entry, and provider statement before reporting settlement.
  6. Use POST /transactions/reverse only for eligible unsettled authorizations/captures. Settled transactions require the chargeback process.
POST /transactions/authorizePOST /transactions/capturePOST /transactions/reversePOST /settlement/batchesGET /settlement/batches/:batchNumber
Production boundary: ISO 8583 build/parse tools and saved host connection records do not by themselves establish a live card-network connection. Confirm the acquirer adapter and end-to-end certification with the deployment operator before accepting real card payments.
Wise pass-through · operator-managed · provider configuration required

5. Receive a Wise bank transfer and pay out to the customer's bank

The separate Rails service is a pass-through: Wise reports an incoming credited transfer, the service matches it to a registered customer, then creates a Wise payout to that customer's saved bank destination. It does not credit the customer's PrimeStack wallet. Without Wise live credentials the payout is simulated.

Step by step

  1. An authorized operator registers the customer and their verified Wise receiving account identifier and destination bank details in the secured Rails console. The account identifier must match the credited Wise account; do not use a customer-supplied reference as the only matching control.
  2. Configure the Wise API key, profile ID, live/sandbox environment, and Wise webhook public key. Test the whole flow in sandbox before switching to live.
  3. Register the public callback URL https://YOUR_HOST/api/rails/webhook in Wise for incoming-transfer#credited. The callback is forwarded to the Rails service, which verifies Wise's RSA-SHA256 signature against the raw request body.
  4. The payer sends funds to the assigned Wise receiving account details. Wait for Wise's credited event; an API health check or a payment instruction is not proof of receipt.
  5. The service matches the credited IBAN/account number to the registered customer. If it cannot match, the transaction is marked UNMATCHED for manual review and is not paid out to a guessed customer.
  6. For a match, the Rails service creates and funds a Wise payout to the saved bank destination. Check the Rails transaction and Wise payout status, then reconcile the incoming transfer, payout reference, and bank confirmation.

External bank action still required

6. Submit a bank withdrawal instruction from a wallet

POST /s2s/withdrawals checks the wallet and connection, posts a debit to the wallet ledger, and creates a withdrawal record. The route itself does not call ACH, SEPA, SWIFT, or another bank network; an approved bank integration or operations team must execute the payment.

Step by step

  1. Confirm the S2S connection is active and belongs to the merchant. Verify wallet ownership, currency, available balance, beneficiary details, fees, and all required approvals.
  2. Call POST /s2s/withdrawals with the wallet, amount, currency, bank name/country, account holder, and at least one supported bank identifier: IBAN, account number, or SWIFT/BIC.
  3. Store the withdrawal ID/reference and inspect GET /s2s/withdrawals/:id. The wallet debit is posted when the instruction is created.
  4. Have the authorized bank executor submit the actual transfer outside this route and obtain the provider's final confirmation/reference.
  5. Only after that evidence is checked should an administrator update the withdrawal status through PATCH /admin/s2s/withdrawals/:id/status, then reconcile the bank statement to the ledger.
Failure handling: Changing a withdrawal to FAILED or CANCELLED does not automatically refund the wallet debit in the current implementation. Follow an approved compensating-entry workflow before closing a failed payout.
Message draft only

7. Create a SWIFT / ISO 20022 payout draft

POST /admin/swift-payouts/draft generates a pacs.008 XML message and identifiers. The response is explicitly DRAFT_NOT_SENT; there is no route here that submits it to a bank.

Step by step

  1. Have an authorized operator validate beneficiary details, bank/BIC information, amounts, currency, settlement date, and message fields against the receiving institution's specification.
  2. Generate the draft using the secured administrator API and review the complete XML and returned message, end-to-end, and UETR references.
  3. Submit the approved instruction using the bank's separately certified channel. Do not mark the payout sent based only on draft generation.
  4. Reconcile the bank's accepted/rejected response and final settlement evidence to the payout and ledger records.
Standalone prototype · not in the standard launcher

8. Crypto payout (USDT on TRC-20 only)

The repository contains a separate service that checks a CRYPTO:USDT ledger balance, broadcasts a TRC-20 transfer, and then posts a ledger entry containing the transaction hash. The standard platform launcher does not start this service.

Current production boundary

  1. Do not expose its POST /withdraw route to the internet or merchant clients: the route currently has no request authentication.
  2. Before any use, an operator must deploy it on a restricted private network, add an authenticated gateway and approval controls, and configure the TRON provider and signer through a secrets manager.
  3. Only the configured USDT TRC-20 asset/network is supported. There is no inbound blockchain deposit listener or customer crypto deposit flow in this service.
  4. If an approved internal test is enabled, verify the broadcast transaction hash and matching ledger reference independently. A broadcast with a failed ledger post requires manual reconciliation.
Do not treat as a supported public payout method until request authentication, operational approvals, and end-to-end reconciliation have been implemented and verified.
Live · operator JWT or signed webhook

9. Receive real funds into a terminal

Two routes record money that already arrived from outside the platform — a bank or VPA settlement, or a partner sender — into a terminal's or merchant's receiving account. Each posts a double-entry credit and is idempotent by its reference or event ID, so a retry never double-credits.

Step by step

  1. Confirm the receiving terminal (or merchant) exists and is active. When the terminal's ledger account is missing for the requested currency, the route creates it before crediting.
  2. For an operator-driven credit, obtain a JWT from POST /admin/login and call POST /t2t/inbound. Only SUPER_ADMIN and ADMIN roles may credit funds this way.
  3. Send a unique reference of 16–128 characters using only A–Z a–z 0–9 . _ : -. Reusing a reference for the same terminal and currency returns the original receipt with duplicate: true instead of crediting twice.
  4. For an automated sender, have them call POST /webhooks/inbound with a 13-digit x-primestack-timestamp (Unix milliseconds, within the configured drift window) and x-primestack-signature = HMAC-SHA256 hex over timestamp + JSON.stringify(body) using the shared inbound secret. A unique eventId (8–128 characters) makes the webhook idempotent.
  5. Store the returned journalEntryRef, accountCode, amount, and currency, then confirm the terminal balance with GET /t2t/balance/:tid?currency=USD and list transfers with GET /t2t/transfers.

Not an external transfer: these routes record funds that have already arrived. They do not pull money from a bank or provider, and a successful response proves only that the ledger was credited — reconcile it against the bank or provider statement.

Not standalone ways to move money

These support an integration, but are not, on their own, completed pay-in or payout rails.

Invoices and payment links

POST /merchant/invoices and POST /merchant/payment-links create request records. The current routes do not provide a checkout, collection confirmation, or settlement callback.

Virtual account records

Admin virtual-account provisioning is gated by Wise configuration. When Wise provisioning is enabled the route returns real Wise receiving-account details (IBAN or local account number); otherwise it stores a local identifier only. Receiving funds into the account is a separate step — use POST /t2t/inbound or the signed POST /webhooks/inbound.

ISO messages and route selection

ISO 8583/20022 tools build, parse, or validate messages. PAG route selection recommends a route only. Neither alone reserves funds, sends a bank payment, or confirms settlement.

Common controls for every production flow

Use the assigned environment's current OpenAPI specification and contract; route access and provider support can differ by deployment.

Authenticate server-side

Keep HMAC keys, connection secrets, Wise credentials, and administrator JWTs out of browser code, mobile apps, URLs, and logs.

Keep a reconciliation record

Store the caller's reference, PrimeStack reference, provider reference, amount, currency, status, timestamps, and final bank/ledger evidence.

Do not assume success

Handle declined, pending, duplicate, unmatched, failed, reversed, and partially completed batch results explicitly. Retry only with the same idempotency key when that endpoint supports it.
